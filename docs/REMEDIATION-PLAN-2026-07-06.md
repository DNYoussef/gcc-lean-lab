# gcc-lean-lab - Remediation Plan (2026-07-06)

## Verdict

Overall: **A-**. Target: **research-ready (formal verification)** - confirmed, no override.
The math is real: 1,892 lines of Lean 4, zero sorry/admit/axiom/native_decide anywhere
(grep-verified), 70 kernel-checked witness examples that fail the build on wrong values,
explicit non-claims (README.md:3-4), green CI (lake build on every push), tagged
v0.1.0-gcc-razor. What holds it below A is not the proofs - it is everything around them:
a README that undercounts and omits ~40% of the repo, a false provenance comment, lake-init

artifact two downstream Python repos pin against) is generated by convention-coupled
duplicate Float code and never regenerated or diffed in CI. All fixes are cheap and
incremental; no rewrites.

- REAL (verified clean): zero proof placeholders across all .lean files; GCC_CanonicalCore.lean

  correct by grader; THEOREM_MAP.md spot-checks 5/5 accurate at the tag.
- THEATER: stale false provenance comment - Capstone.lean:15-16 claims "this file has not been
  compiled in this runtime; no Lean/Lake toolchain is installed here", contradicted by commit
  fae99d8 (first green build), tag v0.1.0-gcc-razor, and CI running lake build.
- THEATER: README inventory rot - README.md:18 undercounts tests by 25; README.md:14-20 omits

  GccLeanLab.lean:1.

## The plan

Order: gate first, then the cross-repo drift hole (highest external blast radius), then the
latent namespace bomb, then docs truth, then deletion/polish.

### PHASE 0 - Reproducible acceptance gate (always first)

Goal: one command that proves the repo end-to-end, hermetic, canary-asserted, in CI.

Gates for THIS project (extend lean_action_ci.yml build job):
1. `lake build` (exists - keep).
2. `lean GCC_CanonicalCore.lean` - the zero-imports island is currently NOT built by lake
   (not a lib module), so CI never checks it. Add as explicit step.
3. Vector conformance gate: `lake exe gccvectors && git diff --exit-code golden_vectors.json`.
   Fails CI if committed vectors differ from what the current source generates.

Fail-first canary: locally perturb one constant in VectorGen.lean (e.g. a KS grid value),
run gate, confirm step 3 goes red; revert. Then perturb one theorem statement in
GCC_CanonicalCore.lean, confirm step 2 goes red; revert. Commit the workflow only after
both canaries demonstrated failure.

Done-when: CI runs all three steps green on an untouched checkout, and both canary
perturbations are documented (commit message or docs note) as having failed the gate.

### PHASE 1 - Close the golden-vector drift channel (correctness, cross-repo)

Goal: make VectorGen coupled by the build, not by comment.

Steps (smallest units):
1. `import GccLeanLab.MetaCalculus` in VectorGen.lean. Reference the proved names
   (GCC.bgTransform etc.) in the provenance string via real identifiers where possible,
   so a rename in MetaCalculus.lean breaks the exe build instead of silently orphaning
   the shadows. Float math stays as-is (Real is noncomputable; shadows are legitimate).
2. Co-locate each Float shadow with a comment-anchored `-- shadows: GCC.<name>` line AND
   a `#check @GCC.<name>` so the anchor is compiler-verified, not prose.
3. Keep output byte-identical: after the import change, `lake exe gccvectors` must produce
   a zero-diff golden_vectors.json (Phase 0 gate proves this automatically).

Fail-first test: before step 1, rename bgTransform locally in MetaCalculus.lean and confirm
today's build stays green (demonstrates the hole); after step 1, same rename must break
`lake build`.

Done-when: renaming any shadowed definition in MetaCalculus.lean fails the build, and
golden_vectors.json is byte-identical to the committed copy.

### PHASE 2 - Defuse the GCC namespace collision (latent correctness)

Goal: GCC.gadd/gmul/gsub/gzero/gone are defined twice in the same namespace
(GCC_CanonicalCore.lean:99-104 over Gen; Capstone.lean:61-77 over Chart). Safe only
because the core is an import-island. R1: fix the structure so the collision cannot occur.

Steps:
1. Fail-first: add GCC_CanonicalCore as a lake lib module in a scratch branch; observe
   ambiguity errors. This is the test.
2. Move Capstone's chart-level generated ops into a sub-namespace (e.g. `GCC.ChartOps`)
   or rename with a `c` prefix. Capstone side moves because the canonical core owns the
   canonical names. Update MetaCalculus.lean and Tests.lean call sites mechanically.
3. Update docs/THEOREM_MAP.md entries touched by the rename (Phase 3 makes this checkable).

Done-when: both files can coexist as built modules without ambiguity (verify in the scratch
branch, then drop the temporary lib entry - the island design stays; only the collision goes).

### PHASE 3 - Docs truth (theater removal)

Goal: README and THEOREM_MAP say only true, checkable things.

Steps:
1. Delete Capstone.lean:15-16 stale "never compiled here" comment (2-line diff).
2. README.md: fix "~45" -> "70 witness examples" (README.md:18); add Contents rows for
   GccLeanLab/MetaCalculus.lean, GccLeanLab/VectorGen.lean + `lake exe gccvectors`, and
   golden_vectors.json with its two downstream consumers named.
3. THEOREM_MAP.md pins theorems by hardcoded line numbers "from the v0.1.0-gcc-razor tag"
   (THEOREM_MAP.md:3). Do not chase line numbers by hand. Replace line pins with name
   anchors, and add a CI shell step that greps each mapped `theorem <name>` in its claimed
   file and fails on a miss (a ~15-line script step in lean_action_ci.yml; no new tooling).
   Line numbers may stay as "as of tag X" hints but names are the contract.

Fail-first test: add a deliberately wrong theorem name to THEOREM_MAP.md, confirm the new
CI step fails; revert.

Done-when: CI theorem-map check green; README counts match `grep -cE '^example'` output;
no prose claim in the repo contradicts git history.

### PHASE 4 - Delete dead code (R12)

Steps:
1. Delete GccLeanLab/Basic.lean; remove `import GccLeanLab.Basic` from GccLeanLab.lean:1.
2. docs/relay-artifacts/: delete the retired capstone draft, patch, and zip from the working

Done-when: `lake build` green with Basic.lean gone; no unbuilt .lean or binary blobs in the

### PHASE 5 - Hardening polish (last, optional)

Steps:
1. lean_action_ci.yml: scope `pages: write` + `id-token: write` to the docgen job only;
   keep workflow-level `contents: read`. Pin actions/checkout and both leanprover actions
   by commit SHA.
2. Narrow Capstone.lean:22 `import Mathlib` to targeted modules ONLY if a Mathlib bump is
   planned; the payoff is compile time + removing the fragility that forced the 4-way
   `first | ...` shim at MetaCalculus.lean:144-148. Incremental: replace the wholesale
   import, fix breakage module-by-module, then try deleting the shim.

Done-when: CI green with scoped permissions and pinned SHAs; (optional) build compiles
against targeted imports with the shim reduced or removed.

## Do not break

- golden_vectors.json values and JSON shape: meta-calculus-toolkit (Railway-live) and
  the-agent-maker pin against it with rtol assertions. Every phase must leave the file
  byte-identical unless a coordinated cross-repo bump is planned. The Phase 0 diff gate
  enforces this automatically.
- Theorem names are the public API (THEOREM_MAP.md, downstream docs, Igor-style doc-truth
  tooling). Phase 2 renames only the colliding Capstone-side ops; core names untouched.
- GCC_CanonicalCore.lean stays a zero-imports island - that property is a documented claim
  (line 3) and a design feature. Check it in CI; do not fold it into the lib.
- Tag v0.1.0-gcc-razor and the green main branch stay untouched; all work on a branch,
  merged only with the full Phase 0 gate green.
- RETRACTED CLAIM GUARD: bigeometric-2nd-order was retracted (2026-06-12 GCC validation
  sweep). No phase may reintroduce a 2nd-order bigeometric theorem, vector section, or doc
  claim. If any relay-artifact or draft contains it, that is Phase 4 deletion material,
  not restoration material.
- No Railway/PyPI surface in this repo itself; the constraint is purely the vectors file
  and names above.
